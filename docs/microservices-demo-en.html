What are microservices?

Picture a restaurant with specialized staff: the chef handles cooking, the server handles table service, and the cashier handles payments. Each person does one thing — and does it well. If the cashier calls in sick, the restaurant can still serve food; the chef doesn't stop.

Microservices work the same way in software. Instead of one giant program that does everything (called a monolith), you break the application into several smaller programs, each with a clear responsibility and its own database.

🏗️
Monolith vs. Microservices

A monolith is like a Swiss Army knife: it does everything, but improving one part means touching all the others. Microservices are like a toolbox: each tool is specialized and can be upgraded or replaced on its own.

Real-world benefits

  • Independent scaling: if the Payments service takes more load, scale only it — no need to scale the entire catalog
  • Separate deployments: one team ships a new version of the Orders service without touching anything else
  • Different tech stacks: one service can use PostgreSQL, another MongoDB — each picks the right tool for its problem
  • Failure isolation: if the Notifications worker crashes, users can still place orders

Challenges (honesty first)

  • Service-to-service communication adds complexity and latency
  • Debugging an issue that spans three services is harder than debugging a monolith
  • You need to manage multiple databases, configurations, and deployments
  • For small applications, microservices are often overkill
💡
When should you use microservices?

Microservices shine in large systems with multiple teams working in parallel, where different parts of the system have different load profiles. For a solo small project, a well-organized monolith is often the right call.

Code organization (per service)

Each service follows the same layered structure inspired by Domain-Driven Design (DDD):

Catalog/
├── Catalog.Domain/          ← Pure business rules (no external dependencies)
│   ├── Entities/            ← Product (the core aggregate)
│   └── Repositories/        ← Interface (contract) for the repository
│
├── Catalog.Application/     ← Use cases, DTOs, orchestration
│   ├── DTOs/                ← What goes in and out of the API
│   └── Services/            ← ProductService (application logic)
│
├── Catalog.Infrastructure/  ← Technical details (database, external HTTP)
│   ├── Persistence/         ← DbContext + EF Core Migration
│   └── Repositories/        ← Concrete repository implementation
│
└── Catalog.Api/             ← HTTP entry point
    ├── Controllers/         ← Receives requests, delegates to Service
    └── Program.cs           ← Application bootstrap
📐
Why this separation?

The Domain layer has no knowledge of databases, HTTP, or any technology. That means you can swap PostgreSQL for MySQL tomorrow without touching any business rules. This is the Dependency Inversion Principle (DIP) from SOLID in action.

1 Phase 1 — Product Catalog

The Catalog service is the starting point. It manages products: creation, updates, deletion, and paginated queries with category filtering. The patterns introduced here are reused by all other services.

Concepts introduced

📦
Database per Service

Each microservice owns its own database. The Catalog uses PostgreSQL on port 5433. No other service accesses that database directly — if you want a product, you call the Catalog API. This guarantees autonomy and independence between services.

Entity Framework Core + Migrations

EF Core is the ORM (object-relational mapper) used to interact with the database. Instead of writing SQL by hand, you define C# classes (called entities) and EF Core generates the SQL automatically. Migrations are version-controlled scripts that evolve the database schema as the code changes.

Catalog.Domain/Entities/Product.cs
public class Product
{
    // EF Core requires a parameterless constructor (can be private)
    private Product() { }

    // Static factory methods — full control over object creation
    public static Product Create(string name, decimal price, int stock)
    {
        return new Product
        {
            Id            = Guid.NewGuid(),
            Name          = name,
            Price         = price,
            StockQuantity = stock,
            CreatedAt     = DateTime.UtcNow,
            IsActive      = true
        };
    }

    public Guid    Id            { get; private set; }
    public string  Name          { get; private set; } = "";
    public decimal Price         { get; private set; }
    public int     StockQuantity { get; private set; }
    public bool    IsActive      { get; private set; }
}
🔒
Why private set?

With private set, an object's internal state can only be changed through its own methods. This prevents external code from putting the entity into an invalid state — for example, a negative price.

2 Phase 2 — Orders Service

The Orders service demonstrates how microservices communicate synchronously — one calls another and waits for a response. When an order is created, the Orders service queries the Catalog to validate that products exist and have enough stock.

Pattern: product snapshot

⚠️
Problem: what if the price changes later?

If an order only stored a product ID, and the price changed in the Catalog, the old order's total would be wrong. This is a real issue in e-commerce systems.

The solution is to capture a snapshot of the product at order creation time: the name and price are copied into the order item and become immutable. Even if the Catalog changes tomorrow, the order history stays correct.

Orders.Domain/Entities/OrderItem.cs
public class OrderItem
{
    // Snapshot captured at order creation time
    public string  ProductName { get; private set; } = "";
    public decimal UnitPrice   { get; private set; }
    public int     Quantity    { get; private set; }

    // Computed in memory — EF Core ignores this property in the database
    public decimal Subtotal => UnitPrice * Quantity;
}

HTTP resilience

The Orders service calls the Catalog over HTTP. What happens if the Catalog is slow or unavailable? The Microsoft.Extensions.Http.Resilience package adds automatic behaviors:

MechanismWhat it does
Total timeoutCancels the request if it takes more than 30 s overall
Retry with jitterRetries up to 3 times with a random delay (prevents synchronized thundering herds)
Circuit BreakerIf too many requests fail, stops calling the troubled service for a cooling-off period
Orders.Infrastructure/DependencyInjection.cs
services
    .AddHttpClient<ICatalogClient, CatalogHttpClient>(client =>
    {
        client.BaseAddress = new Uri(configuration["CatalogServiceUrl"]!);
    })
    .AddStandardResilienceHandler();  // retry + circuit breaker + timeout

3 Phase 3 — Payments Service

The Payments service processes charges. In production it would call a real API like Stripe or Braintree. In this lab we use a Fake Provider that simulates different scenarios so you can explore resilience patterns without real money.

Circuit Breaker — the software breaker switch

The Circuit Breaker is a fundamental pattern in distributed systems. Think of it as an electrical breaker: when there's an overload (too many consecutive failures), it "trips" and stops new requests from reaching the troubled service. After a cooldown period, it "half-opens" to test whether the service has recovered.

         ┌──────────────────────────────────────────────────────────┐
         │                   CIRCUIT BREAKER                       │
         │                                                          │
         │  CLOSED   ──► too many failures ──►  OPEN               │
         │  (normal)                            (blocks requests)  │
         │     ▲                                    │              │
         │     │                                    ▼              │
         │     └──── success ────  HALF-OPEN                       │
         │                         (tests 1 request)               │
         └──────────────────────────────────────────────────────────┘
Payments.Infrastructure/DependencyInjection.cs
services.AddHttpClient<IPaymentProviderClient, FakePaymentProviderClient>()
    .AddResilienceHandler("payments", pipeline =>
    {
        pipeline.AddTimeout(TimeSpan.FromSeconds(15));      // overall timeout
        pipeline.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            Delay            = TimeSpan.FromMilliseconds(500),
            UseJitter        = true                // randomized wait
        });
        pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio      = 0.5,  // trips at 50 % failure rate
            SamplingDuration  = TimeSpan.FromSeconds(30),
            MinimumThroughput = 5,    // needs at least 5 requests
            BreakDuration     = TimeSpan.FromSeconds(10)
        });
    });

4 Phase 4 — Asynchronous Events

Up to now, services communicated synchronously: one called another and waited. But what if you want other systems to react to something that happened — without the original service needing to know about all of them?

That's where domain events and a message broker come in.

📬
Analogy: postal mail

Synchronous communication is like a phone call: you must wait for someone to pick up. Asynchronous communication is like sending a letter: you drop it in the mailbox and carry on with your day. Whoever receives it decides what to do with it, and when.

RabbitMQ — the message broker

RabbitMQ is a message broker: a middleman that receives messages from publishers and delivers them to consumers. Services don't need to know each other — they only need to know RabbitMQ.

Two events are published in this lab:

BuildingBlocks.Contracts/Events/
// Published by the Orders service when an order is confirmed
public record OrderConfirmed(
    Guid     OrderId,
    string   CustomerName,
    string   CustomerEmail,
    decimal  TotalAmount,
    DateTime ConfirmedAt
);

// Published by the Payments service when a payment is approved
public record PaymentApproved(
    Guid     PaymentId,
    Guid     OrderId,
    decimal  Amount,
    string   Currency,
    string   TransactionId,
    string   CustomerEmail,
    DateTime ApprovedAt
);

MassTransit — the abstraction over RabbitMQ

Working directly with the RabbitMQ API is verbose. MassTransit is a library that abstracts it away: you think only about publishing and consuming messages, without worrying about channels, exchanges, and bindings.

Orders.Application/Services/OrderService.cs — publishing an event
// The Orders service doesn't know who will receive this event.
// It could be Notifications, Analytics, another system — doesn't matter.
await _publishEndpoint.Publish(new OrderConfirmed(
    order.Id,
    order.CustomerName,
    order.CustomerEmail,
    order.TotalAmount,
    DateTime.UtcNow
));
Notifications.Worker/Consumers/OrderConfirmedConsumer.cs — consuming
public class OrderConfirmedConsumer : IConsumer<OrderConfirmed>
{
    public Task Consume(ConsumeContext<OrderConfirmed> context)
    {
        var evt = context.Message;
        _logger.LogInformation(
            "[NOTIFICATION] Order {OrderId} confirmed for {Email} — ${Total}",
            evt.OrderId, evt.CustomerEmail, evt.TotalAmount);

        // In production: send email, push notification, SMS...
        return Task.CompletedTask;
    }
}
🎯
Loose coupling

The Orders service publishes OrderConfirmed and forgets about it. Tomorrow you can add an Analytics service that also consumes that event without changing a single line of Orders code.

5 Phase 5 — Observability

With several services running, how do you know what's happening? How do you track down a bug that occurred at 3 AM? Observability is the set of practices that lets you understand the internal behavior of a system from its outputs.

This project implements two of the three observability pillars: structured logging and distributed tracing.

Correlation ID — the thread that ties it all together

When a request arrives at the Gateway, passes through the Orders service, which then calls the Catalog — how do you know that all three log lines belong to the same operation?

The Correlation ID is a unique identifier generated for each request and propagated to every service involved. It appears in the X-Correlation-ID HTTP header and in every log line.

Client ─► Gateway  ──► Orders  ──► Catalog
          X-Corr: abc   X-Corr: abc   X-Corr: abc

LOG (Orders):  {"correlationId":"abc","orderId":"...","event":"OrderCreated"}
LOG (Catalog): {"correlationId":"abc","productId":"...","event":"StockChecked"}
               ↑
               Same ID! You can reconstruct the full request path.

OpenTelemetry + structured logs with Serilog

All instrumentation is centralized in BuildingBlocks.Observability, a shared library. Any new service calls builder.AddObservability("service-name") and immediately gets everything:

CapabilityLibraryWhat you get
Structured logsSerilog + CompactJsonFormatterJSON logs ready for tools like Kibana or Grafana Loki
HTTP tracingOpenTelemetryAutomatic spans for every inbound and outbound HTTP request
Correlation IDCustom middlewareID propagated across all services and logs

6 Phase 6 — JWT Authentication

Up to now anyone could create products, place orders, and process payments. Phase 6 protects the write routes with JWT (JSON Web Tokens) — an open standard for securely transmitting authentication information.

🎟️
What is a JWT?

Think of it as an event wristband. You go to the entrance, show your ID (credentials), and receive a wristband signed by the organizer. From that point on, at any restricted area you just show the wristband — no need to show your ID again. The wristband has an expiry date and a signature no one can forge.

Authentication flow

  1. Client requests a token
  ─────────────────────────────────────────────────────────────────────
  POST http://localhost:5100/auth/token
  Body: { "clientId": "demo-client", "clientSecret": "demo-secret" }

  Response:
  { "accessToken": "eyJhbGciOiJIUzI1NiIs...", "tokenType": "Bearer" }

  2. Client uses the token on protected routes
  ─────────────────────────────────────────────────────────────────────
  POST http://localhost:5100/api/orders
  Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

  3. Gateway forwards the token to the destination service
  ─────────────────────────────────────────────────────────────────────
  YARP (Gateway) ──► Orders Service
  Authorization: Bearer eyJhbGciOiJIUzI1NiIs... (copied unchanged)

  4. Service validates the token
  ─────────────────────────────────────────────────────────────────────
  ✅ Valid signature? Not expired? Correct issuer/audience?
     → Allows the operation
  ❌ Any problem → 401 Unauthorized

Which routes are protected?

ServiceRouteProtection
CatalogGET /api/products*Public
CatalogPOST / PUT / DELETE /api/products🔒 JWT required
OrdersGET /api/orders*Public
OrdersPOST /api/orders, /confirm, /cancel🔒 JWT required
PaymentsGET /api/payments*Public
PaymentsPOST /api/payments🔒 JWT required
⚠️
For lab use only!

The POST /auth/token endpoint uses hardcoded credentials (demo-client / demo-secret). In production, replace this with a real identity provider such as Keycloak, Auth0, or Azure AD B2C.

Shared signing key

All services need to validate the same token, so they all use the same signing key (HS256). It's injected via environment variable — never baked into a Docker image.

docker-compose.yml (excerpt)
catalog-api:
  environment:
    Jwt__SigningKey: "your-secret-key-here-change-in-production"
    Jwt__Issuer:     "microservices-demo"
    Jwt__Audience:   "microservices-demo"
