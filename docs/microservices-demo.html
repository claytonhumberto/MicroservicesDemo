O que são microserviços?

Imagine um restaurante com funcionários especializados: o cozinheiro cuida da comida, o garçom cuida do atendimento, e o caixa cuida dos pagamentos. Cada um faz uma coisa só — e muito bem. Se o caixa fica doente, o restaurante ainda pode servir comida; o cozinheiro não para.

Microserviços funcionam da mesma forma no software. Em vez de um único programa gigante que faz tudo (chamado de monolito), você divide a aplicação em vários programas menores, cada um com uma responsabilidade clara e seu próprio banco de dados.

🏗️
Monolito vs. Microserviços

Um monolito é como um canivete suíço: faz tudo, mas é difícil de melhorar uma peça sem mexer nas outras. Microserviços são como uma caixa de ferramentas: cada ferramenta é especializada e pode ser trocada ou melhorada individualmente.

Benefícios no mundo real

  • Escalabilidade independente: se o serviço de pagamentos recebe mais carga, você aumenta só ele — sem escalar o catálogo de produtos
  • Deploy separado: uma equipe pode publicar novas versões do serviço de pedidos sem parar o resto da aplicação
  • Tecnologias diferentes: um serviço pode usar PostgreSQL, outro MongoDB — cada um usa o que faz mais sentido para o seu problema
  • Isolamento de falhas: se o serviço de notificações cair, os usuários ainda conseguem fazer pedidos

Desafios (honestidade em primeiro lugar)

  • Comunicação entre serviços adiciona complexidade e latência
  • Depurar um problema que envolve 3 serviços diferentes é mais difícil do que depurar um monolito
  • Você precisa gerenciar múltiplos bancos de dados, configurações e deploys
  • Para aplicações pequenas, microserviços podem ser um exagero
💡
Quando usar?

Microserviços brilham em sistemas grandes, com múltiplas equipes trabalhando em paralelo, onde partes do sistema têm cargas diferentes. Para um projeto solo pequeno, um monolito bem organizado é muitas vezes a escolha certa.

Organização do código (por serviço)

Cada serviço segue a mesma estrutura em camadas inspirada no Domain-Driven Design (DDD):

Catalog/
├── Catalog.Domain/          ← Regras de negócio puras (sem dependências externas)
│   ├── Entities/            ← Product (a entidade principal)
│   └── Repositories/        ← Interface (contrato) do repositório
│
├── Catalog.Application/     ← Casos de uso, DTOs, orquestração
│   ├── DTOs/                ← O que entra e sai da API
│   └── Services/            ← ProductService (lógica de aplicação)
│
├── Catalog.Infrastructure/  ← Detalhes técnicos (banco, HTTP externo)
│   ├── Persistence/         ← DbContext + Migration do EF Core
│   └── Repositories/        ← Implementação concreta do repositório
│
└── Catalog.Api/             ← Ponto de entrada HTTP
    ├── Controllers/         ← Recebe requisições, delega ao Service
    └── Program.cs           ← Configuração da aplicação
📐
Por que essa separação?

O Domain não sabe que existe banco de dados, HTTP, ou qualquer tecnologia. Isso significa que você pode trocar o PostgreSQL por MySQL amanhã sem tocar nas regras de negócio. É o princípio de inversão de dependência (DIP) do SOLID na prática.

1 Fase 1 — Catálogo de Produtos

O serviço de Catálogo é o ponto de partida. Ele gerencia produtos: criação, atualização, remoção e consultas com paginação e filtro por categoria. Aqui são introduzidos os principais padrões que todos os outros serviços também usarão.

Conceitos introduzidos

📦
Database per Service

Cada microserviço tem o seu próprio banco de dados. O serviço de Catálogo usa o PostgreSQL na porta 5433. Nenhum outro serviço acessa esse banco diretamente — se quiser um produto, precisa chamar a API do Catálogo. Isso garante autonomia e independência entre os serviços.

Entity Framework Core + Migrations

O EF Core é o ORM (mapeador objeto-relacional) usado para interagir com o banco. Em vez de escrever SQL na mão, você define classes C# (chamadas de entidades) e o EF Core gera o SQL automaticamente. As migrations são scripts controlados por versão que evoluem o schema do banco de dados conforme o código muda.

Orders.Domain/Entities/Product.cs
public class Product
{
    // EF Core exige um construtor sem parâmetros (pode ser privado)
    private Product() { }

    // Métodos estáticos de fábrica — controle total sobre a criação
    public static Product Create(string name, decimal price, int stock)
    {
        return new Product
        {
            Id            = Guid.NewGuid(),
            Name          = name,
            Price         = price,
            StockQuantity = stock,
            CreatedAt     = DateTime.UtcNow,
            IsActive      = true
        };
    }

    public Guid    Id            { get; private set; }
    public string  Name          { get; private set; } = "";
    public decimal Price         { get; private set; }
    public int     StockQuantity { get; private set; }
    public bool    IsActive      { get; private set; }
}
🔒
Por que private set?

Com private set, o estado interno do objeto só pode ser alterado pelos próprios métodos da classe. Isso evita que código externo coloque a entidade em um estado inválido — por exemplo, um preço negativo.

2 Fase 2 — Serviço de Pedidos

O serviço de Pedidos demonstra como microserviços se comunicam entre si de forma síncrona (um chama o outro e espera a resposta). Quando um pedido é criado, o serviço de Pedidos consulta o Catálogo para validar se os produtos existem e têm estoque suficiente.

Padrão: Snapshot de produto

⚠️
Problema: e se o preço mudar depois?

Se um pedido só guardasse o ID do produto, e o preço mudasse no Catálogo, o valor do pedido antigo ficaria errado. Isso é um problema real em e-commerces.

A solução é capturar um snapshot do produto no momento da criação do pedido: nome e preço são copiados para o item do pedido e ficam imutáveis. Mesmo que o Catálogo mude amanhã, o histórico de pedidos continua correto.

Orders.Domain/Entities/OrderItem.cs
public class OrderItem
{
    // Snapshot capturado no momento da criação do pedido
    public string  ProductName { get; private set; } = "";
    public decimal UnitPrice   { get; private set; }
    public int     Quantity    { get; private set; }

    // Calculado em memória — EF Core ignora esta propriedade no banco
    public decimal Subtotal => UnitPrice * Quantity;
}

Resiliência na comunicação HTTP

O serviço de Pedidos chama o Catálogo via HTTP. Mas o que acontece se o Catálogo estiver lento ou indisponível? O pacote Microsoft.Extensions.Http.Resilience adiciona comportamentos automáticos:

MecanismoO que faz
Timeout totalCancela a requisição se demorar mais de 30s no total
Retry com jitterTenta de novo até 3x, com espera aleatória (evita sobrecarga sincronizada)
Circuit BreakerSe muitas requisições falharem, para de chamar o serviço por um tempo (protege o sistema)
Orders.Infrastructure/DependencyInjection.cs
services
    .AddHttpClient<ICatalogClient, CatalogHttpClient>(client =>
    {
        client.BaseAddress = new Uri(configuration["CatalogServiceUrl"]!);
    })
    .AddStandardResilienceHandler();  // retry + circuit breaker + timeout

 Pending ──► Confirmed ──► Paid
    │
    └──► Cancelled

POST /api/orders — cria pedido (requer JWT)
POST /api/orders/{id}/confirm — confirma pedido (requer JWT)

3 Fase 3 — Serviço de Pagamentos

O serviço de Pagamentos processa cobranças. Em produção, ele chamaria uma API real como Stripe ou PagSeguro. Neste laboratório, usamos um Fake Provider (provedor fictício) que simula diferentes cenários.

Circuit Breaker — o disjuntor do software

O Circuit Breaker é um padrão fundamental em sistemas distribuídos. Pense nele como um disjuntor elétrico: quando há uma sobrecarga (muitas falhas consecutivas), ele "abre" e impede que mais requisições cheguem ao serviço problemático. Depois de um tempo, ele "meio-abre" para testar se o serviço se recuperou.

         ┌──────────────────────────────────────────────────────────┐
         │                  CIRCUIT BREAKER                        │
         │                                                          │
         │  FECHADO  ──► muitas falhas ──►  ABERTO                 │
         │  (normal)                       (bloqueia requisições)  │
         │     ▲                               │                    │
         │     │                               ▼                    │
         │     └──── sucesso ────  MEIO-ABERTO                     │
         │                        (testa 1 requisição)              │
         └──────────────────────────────────────────────────────────┘

No projeto, a configuração do Payments é mais explícita que a do Orders, porque queremos demonstrar os parâmetros:

Payments.Infrastructure/DependencyInjection.cs
services.AddHttpClient<IPaymentProviderClient, FakePaymentProviderClient>()
    .AddResilienceHandler("payments", pipeline =>
    {
        pipeline.AddTimeout(TimeSpan.FromSeconds(15));      // timeout total
        pipeline.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            Delay            = TimeSpan.FromMilliseconds(500),
            UseJitter        = true              // espera aleatória
        });
        pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio            = 0.5,   // abre com 50% de falha
            SamplingDuration        = TimeSpan.FromSeconds(30),
            MinimumThroughput       = 5,     // precisa de pelo menos 5 req.
            BreakDuration           = TimeSpan.FromSeconds(10)
        });
    });

4 Fase 4 — Comunicação Assíncrona com Eventos

Até aqui, os serviços se comunicavam de forma síncrona: um chama o outro e aguarda a resposta. Mas e se quisermos que outros sistemas reajam a algo que aconteceu — sem que o serviço original precise saber de todos eles?

É aqui que entram os eventos de domínio e o sistema de mensageria.

📬
Analogia: o correio

Comunicação síncrona é como ligar para alguém: você precisa esperar atender. Comunicação assíncrona é como enviar uma carta: você deposita no correio e continua seu dia. Quem receber a carta decide o que fazer, quando quiser.

RabbitMQ — o mensageiro

O RabbitMQ é um message broker: um intermediário que recebe mensagens de quem publica e entrega para quem consome. Os serviços não precisam se conhecer diretamente — eles só precisam conhecer o RabbitMQ.

Dois eventos são publicados neste laboratório:

BuildingBlocks.Contracts/Events/
// Publicado pelo serviço de Pedidos quando um pedido é confirmado
public record OrderConfirmed(
    Guid     OrderId,
    string   CustomerName,
    string   CustomerEmail,
    decimal  TotalAmount,
    DateTime ConfirmedAt
);

// Publicado pelo serviço de Pagamentos quando um pagamento é aprovado
public record PaymentApproved(
    Guid     PaymentId,
    Guid     OrderId,
    decimal  Amount,
    string   Currency,
    string   TransactionId,
    string   CustomerEmail,
    DateTime ApprovedAt
);

MassTransit — a abstração sobre o RabbitMQ

Trabalhar diretamente com a API do RabbitMQ é verbose. O MassTransit é uma biblioteca que abstrai isso: você só pensa em publicar e consumir mensagens, sem se preocupar com canais, exchanges e bindings.

Orders.Application/Services/OrderService.cs — publicando um evento
// O serviço de Pedidos não sabe quem vai receber este evento
// Pode ser notificações, analytics, outro sistema — não importa
await _publishEndpoint.Publish(new OrderConfirmed(
    order.Id,
    order.CustomerName,
    order.CustomerEmail,
    order.TotalAmount,
    DateTime.UtcNow
));
Notifications.Worker/Consumers/OrderConfirmedConsumer.cs — consumindo
public class OrderConfirmedConsumer : IConsumer<OrderConfirmed>
{
    public Task Consume(ConsumeContext<OrderConfirmed> context)
    {
        var evt = context.Message;
        _logger.LogInformation(
            "[NOTIFICAÇÃO] Pedido {OrderId} confirmado para {Email} — R${Total}",
            evt.OrderId, evt.CustomerEmail, evt.TotalAmount);

        // Em produção: enviar e-mail, push notification, SMS...
        return Task.CompletedTask;
    }
}
🎯
Baixo acoplamento

O serviço de Pedidos publica OrderConfirmed e esquece. Amanhã você pode adicionar um serviço de Analytics que também consome esse evento, sem alterar uma linha do código de Pedidos.

5 Fase 5 — Observabilidade

Com vários serviços rodando, como você sabe o que está acontecendo? Como encontra um bug que ocorreu às 3h da manhã? Observabilidade é o conjunto de práticas que te permite entender o comportamento interno de um sistema a partir de suas saídas.

Este projeto implementa dois dos três pilares da observabilidade: logs estruturados e rastreamento distribuído.

Correlation ID — o fio que conecta tudo

Quando uma requisição chega no Gateway, passa pelo serviço de Pedidos, que chama o Catálogo — como você sabe que os três logs dizem respeito à mesma operação?

O Correlation ID é um identificador único gerado para cada requisição e propagado para todos os serviços envolvidos. Ele aparece no cabeçalho X-Correlation-ID de cada requisição HTTP e em cada linha de log.

Cliente ─► Gateway  ──► Orders  ──► Catalog
           X-Corr: abc   X-Corr: abc   X-Corr: abc

LOG (Orders): {"correlationId":"abc", "orderId":"...", "event":"OrderCreated"}
LOG (Catalog): {"correlationId":"abc", "productId":"...", "event":"StockChecked"}
              ↑
              Mesmo ID! Você consegue reconstruir o caminho completo.

OpenTelemetry + Logs estruturados com Serilog

Toda a instrumentação é centralizada no BuildingBlocks.Observability, uma biblioteca compartilhada. Qualquer serviço novo chama apenas builder.AddObservability("nome-do-servico") e já ganha tudo:

CapacidadeBibliotecaO que você ganha
Logs estruturadosSerilog + CompactJsonFormatterLogs em JSON prontos para ferramentas como Kibana ou Grafana Loki
Rastreamento HTTPOpenTelemetrySpans automáticos para cada requisição recebida e enviada
Correlation IDMiddleware próprioPropagação do ID em todos os serviços e logs

6 Fase 6 — Autenticação JWT

Até aqui qualquer pessoa podia criar produtos, pedidos e processar pagamentos. A Fase 6 protege as rotas de escrita com JWT (JSON Web Token) — um padrão aberto para transmitir informações de autenticação de forma segura.

🎟️
O que é um JWT?

É como um crachá de evento. Você vai na entrada, apresenta seu documento (credenciais), e recebe um crachá assinado pelo organizador. A partir daí, em qualquer área restrita você só mostra o crachá — sem precisar mostrar o documento de novo. O crachá tem uma validade e uma assinatura que ninguém consegue falsificar.

Fluxo de autenticação

  1. Cliente pede um token
  ─────────────────────────────────────────────────────────────────────
  POST http://localhost:5100/auth/token
  Body: { "clientId": "demo-client", "clientSecret": "demo-secret" }

  Resposta:
  { "accessToken": "eyJhbGciOiJIUzI1NiIs...", "tokenType": "Bearer" }

  2. Cliente usa o token nas rotas protegidas
  ─────────────────────────────────────────────────────────────────────
  POST http://localhost:5100/api/orders
  Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

  3. Gateway passa o token para o serviço de destino
  ─────────────────────────────────────────────────────────────────────
  YARP (Gateway) ──► Orders Service
  Header Authorization: Bearer eyJhbGciOiJIUzI1NiIs... (copiado)

  4. Serviço valida o token
  ─────────────────────────────────────────────────────────────────────
  ✅ Assinatura válida? Não expirou? Issuer/Audience corretos?
     → Permite a operação
  ❌ Qualquer problema → 401 Unauthorized

Quais rotas são protegidas?

ServiçoRotaProteção
CatálogoGET /api/products*Pública
CatálogoPOST / PUT / DELETE /api/products🔒 JWT obrigatório

⚠️
Apenas para laboratório!

O endpoint POST /auth/token usa credenciais fixas no código (demo-client / demo-secret). Em produção, você substituiria isso por um provedor de identidade real como Keycloak, Auth0 ou Azure AD B2C.

Chave de assinatura compartilhada

Todos os serviços precisam validar o mesmo token, então todos usam a mesma chave de assinatura (HS256). Ela é injetada via variável de ambiente — nunca fica gravada numa imagem Docker.

docker-compose.yml (trecho)
catalog-api:
  environment:
    Jwt__SigningKey: "sua-chave-secreta-aqui-mude-em-producao"
    Jwt__Issuer:     "microservices-demo"
    Jwt__Audience:   "microservices-demo"

ORMMapeador objeto-relacional: conecta objetos C# ao banco SQL.
PublisherCódigo que envia mensagens para uma fila.
RabbitMQMessage broker open-source: entrega mensagens entre serviços.
ResilienceCapacidade de suportar falhas parciais sem cair por completo.
RetryTentar novamente após uma falha, com espera entre tentativas.
ScalarInterface web para testar APIs (substitui o Swagger neste projeto).
SnapshotCópia de dados num momento específico. Ex: preço do produto no pedido.
SpanUnidade de trabalho no rastreamento distribuído (ex: uma chamada HTTP).
YARPYet Another Reverse Proxy: biblioteca Microsoft para criar gateways.
